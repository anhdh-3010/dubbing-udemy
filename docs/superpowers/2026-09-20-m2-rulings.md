# M2 — decisions taken during implementation

Every ruling made while executing `plans/2026-09-20-m2-real-voice.md`, in the
order they were made. These are decisions taken on the author's behalf when
the plan was silent, wrong, or self-contradicting. Each records the decision,
the reasoning, and what it costs if it turns out to be wrong.

This is the M2 counterpart to `2026-09-20-m1-rulings.md`, transcribed from the
ledger kept during the run — `.superpowers/sdd/2026-09-20-m2-real-voice/progress.md`,
which is gitignored and therefore does not otherwise survive the merge to
main. Entries 1-3 are pre-flight rulings made before any task was
implemented; the rest are in task order. Three entries (8, 9, 12) are not
themselves phrased as "Ruling:" in the source ledger — they are plan defects
the implementer found and fixed under the plan's verbatim-first-then-report
rule, independently confirmed by review — but the progress file records them
with the same weight, and they are folded in here for the same reason: the
document exists so these decisions can be audited, not just the ones that
happened to use the word "Ruling".

Spec: `specs/2026-09-20-udemy-realtime-dubbing-design.md` — the binding
authority wherever it and the plan disagree.

## Rulings

### 1. Pre-flight: Ruling: work in the main working tree, on a branch, not an isolated worktree. The skill defaults to an isolated worktree. M2 installs a launchd agent whose plist embeds an absolute path to `server/.venv/bin/python`, and the extension is loaded unpacked into Chrome from an absolute `.output/chrome-mv3` path. Both would point into a temporary directory that gets deleted, and the plan's own commands hardcode `/Users/anhdh/dubbing` throughout. A feature branch gives the protection that matters (nothing lands on main unreviewed) without breaking the two things M2 exists to install. Cost if wrong: the working tree is not isolated from other work during the run.

### 2. Pre-flight, Task 3: Ruling: Task 3 must also widen the test file's `Message` alias. `background.test.ts` declares `type Message = TranslateRequest | FetchCaptionRequest` and the new TTS tests reach the listener through `listener(msg as Message, ...)`. That compiles, but the cast then asserts something false about the value, which is exactly the shape a reviewer flags. Task 3 Step 7 is extended: also import `TtsHealthRequest` and `TtsSpeakRequest` and add them to the alias. Cost if wrong: none — it is a type-only widening.

### 3. Pre-flight, applies to Task 5: Ruling: `DOMException` is permitted inside `src/core/`. The purity constraint names `window`, `document`, `chrome`, `fetch`, `Audio` — the browser-only surfaces that would stop core being testable in Node. `DOMException` is available in Node and is already how the cancellation contract is expressed in `src/core/types.ts` (`Utterance.play` rejects with AbortError). `fallback.ts` uses it only to recognise that contract, not to reach a browser. Cost if wrong: a reviewer objects and it moves behind a tiny predicate — cheap.

### 4. Task 1: Ruling: reviewer is right that `requirements.txt` omits `pydantic` although `app.py`'s import list pulls it in directly — the plan's Step 1 content is what omitted it, so this is the planner's defect, not the implementer's. The file's own comment states direct imports get pinned, so shipping it without pydantic makes the comment false. Fix: pin `pydantic==2.13.5` (the version `uv` actually resolved). Cost if wrong: a redundant pin that fastapi would have supplied anyway — harmless.

### 5. Task 2: Ruling: the health-poll finding is real and worth fixing, though the plan mandated the script verbatim. `install-agent.sh` polls `/health` after bootstrap and treats any 200 as success — it cannot tell the newly bootstrapped process from a stale one still holding the port, so a re-install after editing the plist can report success while the old configuration is what actually answers. This is load-bearing rather than theoretical: Task 10 Step 3 instructs the user to bootout and then re-run `install-agent.sh`, which is exactly the untested path. Fix: after bootstrap, also require `launchctl list <label>` to report a live PID and a last-exit status of 0, so a new instance crash-looping on `EADDRINUSE` is caught instead of being masked by the stale process's own 200. Cost if wrong: ~12 extra lines in an install script, and a stricter check that could in principle fail on a healthy install — which the fix round's own re-install test would catch.

### 6. Task 2: Ruling: fix both new items surfaced by round-2 review rather than parking them. (a) bootout-then-bootstrap races and fails with launchctl's raw `Bootstrap failed: 5: Input/output error` on live re-installs — the re-reviewer confirmed the script prints nothing of its own there because `bootstrap` is unguarded under `set -e`, and the earlier claim that "the script already works around it" was wrong. It reproduces consistently on exactly the path Task 10 tells the user to walk. (b) the new `LastExitStatus = 0` requirement (Ruling 5, above) can false-FAIL a healthy install, because that status is the job label's last exit, not the running instance's — a first spawn that hit a transient `EADDRINUSE` and was silently respawned healthy by `KeepAlive` leaves a stale non-zero status behind a live, working PID.

### 7. Task 2: Ruling: replace the `LastExitStatus` heuristic from Ruling 5 with a decisive check instead of patching it — compare the PID holding port 8770 (`lsof -ti tcp:8770 -sTCP:LISTEN`) against launchd's reported PID for the label. Equal means the agent itself is what answers; that is exactly the question Ruling 5 asked, answered exactly rather than inferred, and it cannot false-fail on a stale exit status. Cost if wrong: depends on `lsof`, which ships with macOS; if it were absent the script fails closed with a clear message rather than passing wrongly.

### 8. Task 3: Plan defect found and fixed under the verbatim-first rule, confirmed independently by the reviewer: (a) the brief's Step 7 `beforeEach` omitted `mod.default.main()`, so all five new tests would have crashed before asserting anything; (b) two `vi.fn(...)` calls needed an explicit `<typeof fetch>` type argument to satisfy `strict` (the same quirk `gemini.test.ts` already works around elsewhere in the codebase). Both fixes are setup/type-only and change no assertion. Cost if wrong: without (a), the five new tests would never have run at all while appearing green by virtue of not executing; without (b), the file would not typecheck.

### 9. Task 4: Plan defect found by the implementer under the verbatim-first rule and confirmed by the reviewer, who reproduced it independently in an isolated scratch file: the brief's `toBytes(): Uint8Array` does not satisfy `BlobPart` under this repo's TypeScript 7.0.2 — `Uint8Array<ArrayBufferLike>` is not assignable where `Uint8Array<ArrayBuffer>` is expected. Fixed by annotating the return type explicitly as `Uint8Array<ArrayBuffer>`. Type-only, no runtime change. Cost if wrong: `tsc --noEmit` fails on this file.

### 10. Task 5: Ruling: fix the Important finding — `markDown`'s announce-suppression guard (`fallback.ts`, the `if (this.announced === 'fallback') return` line) is reached exactly once in every one of the 10 existing tests, so deleting the guard leaves the suite green. The reviewer widened the implementer's framing correctly: the gap is not one missing scenario but zero coverage of the guard itself. Real consequence — a flapping primary (fail → cooldown → fail) would fire a duplicate `onStatusChange('fallback', ...)`, and Task 8 turns those into viewer-facing notices, so the regression would show up as a spurious repeated toast that CI could never catch. One added test (a flap-cycle test, mutation-checked: fails with the guard removed, only that test fails, passes restored) closes it. Cost if wrong: one extra test.

### 11. Task 6: Ruling: fix the Important finding — the `ENHANCED_VOICE` comment stated `"Linh (Enhanced)" in English` as observed fact, but the M1 verification run only ever ran on a Vietnamese-locale machine and only ever recorded `Linh (Nâng cao)`. That is the same category of error M1's own fix-up task existed to correct — a comment asserting an observation nobody made — just pointing the other way. The regex keeps matching all three qualifiers (`enhanced`, `premium`, `nâng cao` — cheap, harmless), but the comment must say which one was actually seen versus which are speculative for other locales. Cost if wrong: none; it is a comment.

### 12. Task 7: Plan defect found by the implementer: the brief's Step 6 preamble dropped `speak()`'s `controller` local while the unchanged tail still used it (`this.speaking = { utterance, controller }`), producing a `tsc` error and a runtime `ReferenceError` on every call to `speak()`. Fixed by having `take()` return `{ utterance, controller }` instead of just the utterance. The reviewer confirmed this is the minimal correct shape and that the `preparing` bookkeeping survives it. Cost if wrong: `speak()` throws on every invocation — the scheduler would never produce a single dubbed sentence.

### 13. Task 7: Ruling (Critical): fix. `maybePrefetch()` invalidates a held prefetch entry only on `spoken.has(held.id)`, but `tick()` only marks a segment spoken when it *selects* one, which needs `now < s.end`. A slot that passes entirely unselected therefore leaves the entry held forever, and the `else return` guard then suppresses every future prefetch — the whole feature silently dies for the rest of the lecture, and one utterance (and, on the real provider, one blob URL) is retained indefinitely. Two ordinary triggers, both reproduced: a long sentence overrunning into the next slot, and a hidden tab (`requestAnimationFrame` suspends while the video keeps playing, so the playhead steps over slots with no seek event in between). Fix: also discard the held entry when the segment it refers to is gone from `this.segments`, or when `currentTime >= segment.end`. Cost if wrong: a slightly eager discard costs one avoidable re-synthesis.

### 14. Task 7: Ruling (Important): fix, and the premise is now measured rather than assumed. The reviewer flagged that `maybePrefetch()` ran *before* selection inside `tick()`, so on the tick after a seek or resume the urgent live `prepare()` for the sentence someone is waiting on was issued *second*, behind a speculative `prepare()` for a sentence up to ten seconds away — but noted this only matters if the server serialises requests. Measured directly on the live server: two concurrent `/v1/audio/speech` calls returned at 0.41s and 0.81s, the second having visibly waited for the first — it serialises. So the viewer's sentence really does queue behind a speculative one at exactly the moment they are waiting for it, roughly doubling its latency, and spec 6.2 converts that delay straight into a higher speaking rate and a slowed-down video. Fix: restructure `tick()` so selection runs before `maybePrefetch()`. Cost if wrong: the restructure touches the most delicate function in the codebase, which is why the fix was required to keep all 28 then-existing tests green and re-verify every interleaving by hand.

### 15. Task 7: Ruling: restoring two assertions the reviewer had flagged as weakened (their Minor 3) is folded into the Important fix's verification above, not treated as a separate minor. Those two tests are the only thing proving nothing is synthesised while the video is paused or the scheduler is stopped, and the tick() restructure edits exactly the code path they guard — they stop being merely cosmetic the moment `maybePrefetch()` moves. Cost if wrong: a regression that starts synthesis while paused/stopped would go undetected.

### 16. Task 7: Ruling: one more fix round for two one-liners the re-review surfaced after round 1. (a) The new `now >= segment.end` discard clause (Ruling 13) and the pre-existing `s.start > now` candidate filter in `maybePrefetch()` are simultaneously satisfiable for a degenerate segment with `end <= start`: every frame would discard the held entry and immediately re-prefetch the same segment, up to roughly 600 aborted POSTs per second against a server measured as serialising (Ruling 14), starving the sentences that actually need it. Judged low severity on its own because it needs malformed input, but `vtt.ts` performs no `start < end` validation and `mergeCues` propagates whatever it is given — M1's whole lesson was that real caption data arrives in shapes nobody predicted. Fix: add `s.end > now` to the candidate filter, making it the exact negation of the discard predicate and the loop impossible. (b) The ordering property the entire round existed to establish — selection before prefetch — was pinned by no test: moving `maybePrefetch()` back above the selection guard left all 29 tests green. Same category as Task 5's previously-uncovered guard (Ruling 10); consistency requires fixing this too. Cost if wrong: two lines and one test.
